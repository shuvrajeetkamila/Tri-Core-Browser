## Architecture and integration boundary

TRI-CORE is an Electron 44.7.0 desktop app. Three sandboxed `WebContentsView` instances render ordinary website tabs inside Chromium. The app can query Electron/Chromium GPU feature/device information, but the public `WebContentsView` API does not expose arbitrary tabs' D3D12/Vulkan textures, game depth/motion vectors, native swap chain, or a compositor synchronization contract. The app does not inspect renderer/GPU-process memory, inject code into remote pages, or weaken the sandbox.

Electron's public `capturePage()` returns a `NativeImage`. That is a valid bounded screenshot boundary, not a live GPU handle, zero-copy transfer or means to return processed output to Chromium's compositor. The screenshot path remains useful for measuring/validating the separate native helper; it is not the selected live integration.

### Chosen vertical slice: app/game-owned WebGPU target

`app/diagnostics/fsr1-webgpu.html` loads a local, sandboxed controlled scene. Its JavaScript:

1. Requests a WebGPU adapter/device and captures adapter identity when Chromium exposes it.
2. Renders an animated game-like scene at half the visible canvas resolution into a WebGPU texture owned by this page.
3. Compiles distinct AMD FSR1 EASU and RCAS WGSL compute pipelines and dispatches them over GPU textures.
4. Uses a separate presentation render pipeline to submit the RCAS result to the visible WebGPU canvas. The image-processing path uses no CPU pixel readback; optional timestamp-query data and explicit post-run validation copies are separate diagnostic readback.
5. Reports adapter/device/shader/pipeline/resource lifecycle, per-stage dispatch counts, submitted/completed frames, source/output dimensions, and queue-completion wall timing (not a GPU timestamp). Runtime accuracy of these checks awaits the packaged Windows gate.

The source architecture is a genuine game-side integration design because the page owns its render target and inserts FSR into its own WebGPU render graph. It does **not** automatically upscale other web pages or third-party games. The app's global automatic mode deliberately excludes this scene-specific path so it cannot imply that the other cores are being upscaled. Manual FSR status is tied to this scene's reported pipeline state and completed frames; packaged smoke and evidence validation passed in run 38287627583, but the per-stage report contents were not inspected, so runtime claims remain unverified until actual `PASS` evidence is reviewed.

The packaged CI gate freezes completed output, copies original/EASU/RCAS textures only for post-processing numerical comparison, and compares actual `capturePage()` canvas samples with the frozen RCAS texture. Those pixels/captures never feed FSR. The numerical check is a sanity baseline, not bit-for-bit AMD shader conformance. A passing queue-completion promise alone is not visible-output verification.

### Retained screenshot diagnostic

The distinct WebGL2 test scene still exercises:

`WebContentsView.capturePage()` PNG → WIC decode/CPU readback → separate app-owned D3D12 FSR1 EASU + RCAS → output PNG/report/preview.

It requires explicit user action and the exact bundled test-scene URL. It measures capture, readback, helper, GPU timestamp (if available), and round-trip costs. It is always labeled **diagnostic-only**; it is not live browser integration. Existing CI evidence for three changing frames at three resolutions was on D3D12 WARP software only (prior source commit `eee56b7`).

## Electron shared-texture investigation

Electron 44.7.0 documents an **experimental** offscreen route:

- `webPreferences.offscreen.useSharedTexture` opts an offscreen `BrowserWindow` into shared-texture paint events; this is not the existing visible `WebContentsView` path.
- Main-process `sharedTexture.importSharedTexture()` / `sendSharedTexture()` and a renderer receiver can carry the imported resource as a `VideoFrame`. Electron's fixture consumes a received `VideoFrame` with WebGPU's external-texture API.
- The API requires explicit frame/resource lifetime management and release. Its documentation does not establish an end-to-end, zero-copy, low-latency product pipeline.
- Electron v44.7.0 contains Windows handle/OSR implementation code, but its shared-texture end-to-end spec is gated to macOS arm64. Source branches are not Windows app-level round-trip evidence.

Official references: [shared-texture API](https://github.com/electron/electron/blob/v44.7.0/docs/api/shared-texture.md), [offscreen rendering](https://github.com/electron/electron/blob/v44.7.0/docs/tutorial/offscreen-rendering.md), [imported frame lifetime](https://github.com/electron/electron/blob/v44.7.0/docs/api/structures/shared-texture-imported.md), [import texture info](https://github.com/electron/electron/blob/v44.7.0/docs/api/structures/shared-texture-import-texture-info.md), [upstream spec](https://github.com/electron/electron/blob/v44.7.0/spec/api-shared-texture.spec.ts), [WebGPU receiver fixture](https://github.com/electron/electron/blob/v44.7.0/spec/fixtures/api/shared-texture/managed/renderer.js), and [Windows keyed-mutex patch](https://github.com/electron/electron/blob/v44.7.0/patches/chromium/osr_shared_texture_remove_keyed_mutex_on_win_dxgi.patch).

**Decision:** do not switch existing normal `WebContentsView` tabs to offscreen capture. A product route would need separate offscreen contents, correct input/navigation/permission forwarding, resource release and GPU synchronization, a visible presentation surface, resize/occlusion/device-loss/adapter-mismatch behavior, security/packaging coverage, and ongoing compatibility with an experimental API. Windows delivery, page interaction, capture overhead, and visible-output correctness remain unverified. A time-boxed Windows prototype may test this candidate, but it must not be described as live integration unless the complete path passes.

## Milestone 4 research: confirmed APIs versus hypotheses

**Confirmed from primary documentation:** Chromium's Viz display compositor aggregates browser and renderer surfaces before presentation ([RenderingNG architecture](https://developer.chrome.com/docs/chromium/renderingng-architecture)); Chromium video may follow its own surface/overlay path rather than behaving like an ordinary DOM texture ([VideoNG](https://developer.chrome.com/docs/chromium/videong)); WebGPU can import a video element or `VideoFrame` as an external texture, with origin/security validation and limited cross-browser availability ([WebGPU importExternalTexture](https://developer.mozilla.org/en-US/docs/Web/API/GPUDevice/importExternalTexture)); and Windows Graphics Capture uses system UI to select a window/display and delivers D3D11 frames ([Microsoft screen-capture API](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)). AMD describes FSR1 as spatial upscaling from the current anti-aliased frame without history/motion vectors ([GPUOpen FSR1](https://gpuopen.com/fidelityfx-superresolution/)).

**Not established for this product:** that Electron's Windows shared-texture path works end-to-end at our pinned build; that a normal remote page's video is accessible to this app; that protected media can be captured; that Windows capture can safely/consistently replace or mirror an arbitrary window with acceptable latency; or that any route improves image quality/performance. These remain prototype questions, not capabilities.

**Recommendation:** keep game-owned FSR1 as the only current processing design and keep standard Chromium as the safe page fallback. If a useful browser-adjacent feature is desired, start with a dedicated user-selected still-image/local-video viewer, whose input and output are explicitly owned by the app. If the actual requirement is transparent enhancement of every ordinary page, first time-box an Electron 44.7 Windows offscreen shared-texture proof with input forwarding, visible-output comparison, security/lifetime and performance gates. If it fails, the honest alternatives are a costly maintained Chromium/Viz integration or no all-page feature—not page injection or an overlay mislabeled as browser upscaling.

## NVIDIA Streamline: DLSS SR, Frame Generation, and licensing are separate gates

The official Streamline repository README identifies version 2.14.1. It describes Streamline as an open-source integration framework, but states that DLSS/Streamline binary artifacts are obtained from official release ZIPs (not the source repository), that the DLSS-G plugin is prebuilt-only, and that shipping builds should use production binaries with NVIDIA signatures or verify authenticity. The Streamline source license does **not** by itself grant rights to redistribute proprietary DLSS feature binaries.

The official NVIDIA RTX SDK license document available during this review is dated **23 January 2023** and covers DLSS/NGX SDK use. It describes object-code distribution only as incorporated into a materially functional application, bars standalone SDK redistribution/sublicensing, requires notification to NVIDIA before commercial release of an application incorporating DLSS/NGX, restricts DLSS/NGX applications to NVIDIA-GPU systems (with a stated NVIDIA-vGPU cloud exception), and includes additional security, marking, and other terms. This is a dated document, not a substitute for reviewing the exact license shipped with the chosen current SDK/runtime ZIP and getting legal review before distribution. No terms were accepted and no proprietary binary was downloaded or bundled in this work.

- **DLSS Super Resolution (SR):** native integration in a game renderer. NVIDIA's v2.14.1 guide calls for Streamline initialization, the real D3D12/Vulkan device, per-adapter feature-support checks, render/output-size setup, tagged color input/output/depth/motion-vector/exposure resources, per-frame camera/motion constants, and feature evaluation on a matching frame token/viewport/command list. The guide identifies an NVIDIA-provided application ID for NGX-backed DLSS components (or engine metadata where the current integration guide permits it). Chromium does not expose these game-render inputs for arbitrary tabs.
- **DLSS Frame Generation (FG/DLSS-G):** a different feature/plugin with its own guide and feature ID. Its documented design includes a proxy swap chain/present integration, depth/motion/HUD-less color (and UI where applicable), per-frame constants and valid resource lifetimes, Reflex/frame-pacing coordination, supported OS/HWS/driver/hardware requirements, and production signed plugin checks. The DLSS-G plugin is prebuilt-only. The public NVIDIA getting-started page currently shows its system table for Streamline Plugin 2.10.3; do not assume that version-scoped checklist is identical for 2.14.1—query the selected runtime's feature requirements. FG is not implied by an SR toggle or GPU vendor detection.

The legally and technically legitimate route is to obtain the exact SDK/runtime through NVIDIA's official developer/release channel, review/accept the license applicable to that package, use the required ID/engine metadata, package only permitted production binaries, verify signatures, implement the actual native renderer inputs, and test on supported physical NVIDIA hardware. None of those integration or release gates is met here. DLSS SR and FG remain **not implemented / not tested**; no NVIDIA runtime, signed DLL, model, or weight is bundled.

Primary references: [Streamline v2.14.1 README](https://github.com/NVIDIA-RTX/Streamline/blob/main/README.md), [DLSS SR programming guide](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS.md), [DLSS-G programming guide](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS_G.md), [NVIDIA integration checklist and version-scoped requirements](https://developer.nvidia.com/rtx/streamline/get-started), and [NVIDIA RTX SDK license document (23 Jan 2023)](https://developer.nvidia.com/downloads/nvidia-rtx-sdks-license-23jan2023pdf). This is technical due diligence, not legal advice.

## Required validation gates

- **Local tests/build:** controller/policy tests, source/CSP tests, `npm test`, `npm run build`, syntax checks, and workflow YAML checks. Passing these does not prove a GPU runtime path.
- **Windows packaged WebGPU smoke:** require actual WGSL compilation, EASU/RCAS compute-pipeline creation, at least three successful dispatches of each pass, completed output frames, changing scene input, original/EASU/RCAS texture comparisons, screenshot-sample comparison to frozen output, input/output dimensions, adapter/API identity or explicit unknown status, queue-completion wall timing, and saved diagnostic evidence. CPU copies/screenshots occur only after processing and never feed FSR. Physical-GPU field must remain **NOT RUN** in CI. The separate PNG/WARP smoke remains distinctly labeled diagnostic.
- **Physical GPU:** run on a named real Windows adapter; report adapter model/vendor/driver, API, input/output resolutions, processed frames, captures, and measured timings. No physical GPU has been tested for this source change.
- **General-page support:** remain blocked until a supported Chromium rendering/interop boundary passes Windows synchronization, resource-lifetime, visible output, security, resize/occlusion, upgrade and performance tests.
- **DLSS:** require the exact official release/license review, NVIDIA-provided app ID, production signed runtime authorization, separate SR/FG design and compatible physical hardware before packaging or claims.
